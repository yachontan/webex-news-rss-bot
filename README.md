RSS を集めて重複を除き、カテゴリごとに選んで日本語に要約し、Webex の複数スペースへ毎朝配信します。

Python を書き換えずに YAML だけで運用できるようにしてあります。購読するフィードは `urls.yml`、
配信先は `channels.yml`、記事の振り分けは `categories.yml` で決めます。

## できること

1 回の実行で、次の順に処理します。

**収集**：`urls.yml` のフィードをホスト別に並列取得します（同一ホスト内は 1 秒間隔）。
指定時間内（既定 24 時間）の記事を集め、タイトルと概要の類似度で重複を除きます。
同じ事件を複数の媒体が報じていても 1 本にまとめます。

**振り分け**：`categories.yml` のキーワードで各チャンネルの候補を作り、次の順に調整します。

| 段階 | 何をするか |
|:---|:---|
| 専有配信 | `source_groups` を持つチャンネルが、その群のフィード由来の記事を独占する |
| 優先配信 | `priority: true` のチャンネルが、該当記事を他チャンネルから引き上げる |
| 譲渡 | `defers_to` の指定に従い、より適切なチャンネルへ記事を渡す |
| 再配分 | 件数の少ないチャンネルが持つ記事を、混雑したチャンネルから取り除く |
| 日本語補充 | `min_japanese` を下回るチャンネルへ、日本語記事を追加する |

**選定と要約**：候補が上限（既定 15 件）を超えたら重要度順に絞り、各記事を日本語 110 字以内に要約します。
担い手は 3 通りから選べます。[記事の選定と要約](#記事の選定と要約) を参照してください。

**投稿**：Markdown で組み立て、6000 字を超えたら分割して Webex へ送ります。
Cisco Security Advisory には CVSS のバッジが付きます。最後に、全チャンネルの見出しと天気をまとめた
ダイジェストを 1 通送ります。

該当する記事が 0 件のスペースには何も投稿しません。

## 動作環境

- Python 3.10 以降
- macOS または Windows
- Webex Bot のトークンと、投稿先スペースの ID
- 記事の要約に使う実行系（[記事の選定と要約](#記事の選定と要約) を参照）

依存パッケージは `requirements.txt` にあります。

```
feedparser==6.0.12
requests==2.32.5
python-dotenv==1.0.1
PyYAML==6.0.2
webex_bot>=1.2.8
```

設定 UI（Streamlit）を使う場合のみ `requirements-ui.txt` も入れます。

## セットアップ

### ウィザードを使う

リポジトリを置いたフォルダで、次のファイルをダブルクリックします。

- macOS: `はじめに設定する.command`
- Windows: `はじめに設定する.bat`

仮想環境の作成、依存パッケージの導入、`.env` と各 YAML の生成まで済みます。
ブラウザが開く Streamlit 版と、ターミナルで完結する CLI 版のどちらでも進められます。

ウィザードは既存の設定を上書きする前に `.env.bak-20260920-101530` のような退避ファイルを作ります。
中身は設定そのものなので、**コミットしないでください**。

### 手で設定する

`*.example` をコピーして編集します。

```bash
python3 -m venv .
./bin/pip install -r requirements.txt
cp .env.example .env
cp urls.yml.example urls.yml
cp channels.yml.example channels.yml
cp categories.yml.example categories.yml
```

`.env` に Webex のトークンとスペース ID を書きます。スペース ID がわからないときは、
`check_rooms.py`（CLI）か `起動_スペースID確認UI.command`（ブラウザ）で一覧を出せます。

```bash
./bin/python check_rooms.py
```

## 使い方

```bash
./bin/python webex-news-rss-bot.py [オプション]
```

オプションを何も付けない実行は、収集から投稿までを従来どおり通します。

### 基本

| オプション | 既定 | 説明 |
|:---|:---|:---|
| `--dry-run` | なし | Webex へ送らず、投稿内容をターミナルに表示する |
| `--hours N`, `-t N` | 24 | 何時間前までの記事を集めるか |
| `--weekend-catchup` | なし | 月曜の実行だけ取得期間を 72 時間に広げる（金土日の3日分） |
| `--fallback-items N` | 3 | 期間内に記事が無いフィードから、最新 N 件を追加する。0 で無効 |

### 設定ファイルの差し替え

| オプション | 既定 |
|:---|:---|
| `--categories-file PATH` | `categories.yml` |
| `--urls-file PATH` | `urls.yml` |
| `--channels-file PATH` | `channels.yml` |

### 3段分割

| オプション | 既定 | 説明 |
|:---|:---|:---|
| `--pipeline` | なし | 収集 → 生成 → 投稿を 1 プロセスで通す |
| `--emit-candidates DIR` | なし | 収集だけ行い、`DIR` に書き出して終了する。**投稿しない** |
| `--compose DIR` | なし | `DIR` の候補から選定と要約を作って終了する |
| `--post-from DIR` | なし | 収集せず、`DIR` の内容から配信する |
| `--llm-mode MODE` | `api` | 選定と要約の担い手。`api` / `compose` / `none` |
| `--compose-backend NAME` | `endpoints.yml` の `compose.default` | 生成バックエンド名 |
| `--compose-model MODEL` | バックエンドの `default_model` | 生成に使うモデル |
| `--compose-timeout SEC` | 900 | 生成の制限時間。CLI バックエンドのみ |
| `--run-id ID` | 実行時刻 | 中間ファイルのディレクトリ名 |

### 付属のツール

```bash
./bin/python check_rooms.py       # Bot が参加しているスペースの一覧と ID
./bin/python check_network.py     # 配信前の疎通確認（launchd ラッパーが使う）
./bin/python analyze_filter.py    # カテゴリの合格・不合格を診断する
```

## 設定ファイル

| ファイル | git | 役割 |
|:---|:---:|:---|
| `.env` | 対象外 | トークンと API キー。**絶対にコミットしない** |
| `urls.yml` | 対象外 | 購読するフィードと、天気の取得地点 |
| `channels.yml` | 対象外 | 配信先スペースと、そこへ流すカテゴリ |
| `categories.yml` | 対象外 | カテゴリごとのキーワード |
| `categories-private.yml` | 対象外 | 公開したくないキーワードの上書き |
| `regions.yml` | 対象外 | ダイジェストの時事枠での地域配分 |
| `morning_messages.txt` | 対象外 | 投稿末尾にランダムで付ける一言 |
| `endpoints.yml` | 追跡 | 外部サービスの宛先と、生成バックエンドの定義 |
| `compose_select.md` | 追跡 | 記事の選定への指示 |
| `compose_summarize.md` | 追跡 | 記事の要約への指示 |

git 対象外のファイルには、対応する `*.example` があります。

### `urls.yml`

`feeds:` の下に 3 種類を混ぜて書けます。

```yaml
feeds:
  # 1. 名前を付けた群。channels.yml の source_groups から参照する
  - group: Cisco-Security-Advisories
    urls:
      - https://sec.cloudapps.cisco.com/security/center/psirtrss20/CiscoSecurityAdvisory.xml

  # 2. 天気の取得設定（ダイジェストで使う）
  - weather:
      api_url: https://api.open-meteo.com/v1/forecast
      locations:
        - {label: 東京, lat: 35.6895, lon: 139.6917}

  # 3. 素の URL
  - https://blogs.cisco.com/feed
  - https://www.wired.com/feed/rss
```

### `channels.yml`

配信先ごとに 1 要素です。トークンとスペース ID は `${変数名}` で `.env` を参照します。
環境変数が解決できないチャンネルは、そこだけスキップして他の配信は続けます。

```yaml
channels:
  - name: セキュリティ
    webex_space_id: ${WEBEX_SPACE_ID_SECURITY}
    webex_bot_token: ${WEBEX_BOT_TOKEN_SECURITY}
    categories: [セキュリティ]
    max_items: 15
```

| キー | 説明 |
|:---|:---|
| `name` | 見出しに出る名前。`categories` を省くとカテゴリ名の解決にも使う |
| `webex_space_id` / `webex_bot_token` | 投稿先と認証。`${VAR}` で `.env` を参照する |
| `categories` | 流すカテゴリ名の配列。空なら全カテゴリ |
| `source_groups` | `urls.yml` の `group:` 名。その群の記事をこのチャンネルが専有する |
| `priority` | `true` にすると、該当記事を他チャンネルから引き上げる |
| `defers_to` | 記事をより適切な別チャンネルへ譲る。綴りの誤りは起動時に検出する |
| `min_japanese` | 日本語記事の最低件数。下回ると必須語の条件を外して補充する |
| `max_items` | 1 回の投稿に載せる上限。既定 15、上限 50 |
| `digest` | `true` でダイジェスト専用チャンネルになる |
| `digest_blocks` | ダイジェストに載せる枠。`weather` / `channels` / `jiji` から選ぶ。既定は前 2 つ |
| `weather_format` | `table`（コードブロックの表）か `list`（箇条書き） |

### `categories.yml`

カテゴリ名にキーワードの配列を割り当てます。採点は次のとおりです。

- `!` を頭に付けた語は**必須語**で 3 点
- それ以外の語は 1 点
- **必須語を 1 つ以上含み、合計 4 点以上**で合格

```yaml
セキュリティ:
  - "!脆弱性"
  - "!CVE"
  - ランサムウェア
  - 認証
```

どのキーワードが効いているかは `analyze_filter.py` で確認できます。

社名など公開したくない語は `categories-private.yml` に分けます。起動時に `categories.yml` で読み込みます。

### `.env`

```bash
# Webex（必須）
WEBEX_BOT_TOKEN=
WEBEX_SPACE_ID=
WEBEX_SPACE_ID_SECURITY=        # channels.yml の ${VAR} に対応する分だけ追加する

# 生成バックエンド（--llm-mode compose を使うとき）
CLAUDE_CODE_OAUTH_TOKEN=        # claude setup-token で発行する
COMPOSE_CLAUDE_BIN=             # claude の絶対パス。通常は不要

# API 経路（--llm-mode api を使うとき）
LLM_PROVIDER=anthropic          # anthropic / openai / gemini
ANTHROPIC_API_KEY=
ANTHROPIC_MODEL=claude-haiku-4-5-20251001
ANTHROPIC_RERANK_MODEL=claude-haiku-4-5-20251001

SSL_VERIFY=True                 # 検査する SSL プロキシ環境でのみ False にする
```

## 記事の選定と要約

`--llm-mode` で担い手を選びます。**どのモードでも投稿の見た目は同じ**で、違うのは中身を誰が作るかだけです。

| モード | 担い手 | 課金 | 使いどころ |
|:---|:---|:---|:---|
| `compose` | 手元のコマンド（Claude Code など） | サブスクリプションの枠 | 通常運用 |
| `api` | HTTP API（Anthropic / OpenAI / Gemini） | 従量 | API キーで動かしたいとき |
| `none` | 使わない | なし | 生成が通らないときの退避 |

`none` は選定を得点順の抽出に落とし、要約は RSS の原文を整形して使います。
英語のフィードは英語のまま出ます。品質が落ちるので、投稿の末尾に印が付きます。

### 生成バックエンド

`endpoints.yml` の `compose:` 節で定義します。どれを選んでも、同じ指示ファイルと
同じ JSON の受け渡しで動きます。

| 名前 | 種別 | 既定モデル | 中身 |
|:---|:---|:---|:---|
| `claude` | CLI | `sonnet` | `claude -p --safe-mode` を起動する |
| `codex` | CLI | `gpt-5` | `codex exec` を起動する |
| `anthropic` / `openai` / `gemini` | API | Haiku / gpt-5-mini / 2.5-flash | 要約と同じキーを使う |

コマンドの探し方は 3 段階です。`.env` の `COMPOSE_CLAUDE_BIN`（絶対パス）、`PATH`、
`endpoints.yml` の `search_paths`（`~/.local/bin`、`/opt/homebrew/bin`、`/usr/local/bin`）の順に探します。
launchd から実行されると `PATH` は `/usr/bin:/bin:/usr/sbin:/sbin` だけになるため、3 番目の探索が効きます。

どこにも無ければ、**別の方法へ勝手に切り替えず**「バックエンド X は利用できません」と表示して止まります。
黙って品質が落ちた状態で配信し続けないためです。

### 指示ファイル

生成への指示はリポジトリ直下の 2 ファイルです。バックエンドによらず同じものを使います。

- `compose_select.md``：どの記事を選ぶか
- `compose_summarize.md``：どう要約するか

要約の制約は「日本語 110 字以内、1〜2 文、前置きと改行を付けない、与えられた情報だけで完結させる」です。
RSS の概要が見出しの繰り返しだけの記事には、見出し以上のことを書かせません。

`candidates.json` の本文は RSS 由来の第三者の文章なので、**指示ではなくデータとして扱う**ことを
両ファイルに明記してあります。生成に渡すツールも読み書きだけに制限しています。

### API を呼ばずに済ませる条件

要約は、RSS の概要が次をすべて満たすときは API を呼ばずに原文を使います。

- 100 字以内
- 末尾が `。！？.!?」` のいずれかで終わる
- `&nbsp;` などの HTML エンティティを含まない
- ひらがなカタカナ漢字を 1 文字以上含む

同じ URL の記事が複数のチャンネルに出ても、要約は 1 回だけ作って使い回します。

## 収集 → 生成 → 投稿の3段分割

`--pipeline` を付けると、1 回の実行を 3 段に分けて中間ファイルを残します。
`log/compose/<run_id>/` に置かれ、7 日より古いものは自動で消えます。

| ファイル | 誰が書くか | 中身 |
|:---|:---|:---|
| `state.json` | 収集 | 記事の全量。投稿はこれを正本にする |
| `candidates.json` | 収集 | 生成に渡す候補。**記事の URL を含まない**（ドメインのみ） |
| `selected.json` | 生成 | チャンネルごとに選んだ記事の ID |
| `composed.json` | 生成 | ID と要約文だけ |
| `validation.json` | 投稿 | 検証の結果 |

Webex のトークンとスペース ID は、どのファイルにも書きません。

### 生成結果の検証

投稿する前に、`state.json` を正本として突き合わせます。生成側から受け取るのは**ID の並びと要約文だけ**で、
タイトルもリンクも収集時のデータから取ります。記事のすり替えが起きない形にしてあります。

| 検査 | 落ちたとき |
|:---|:---|
| `run_id` が収集時と一致するか | run 全体を見送る（前日の生成物を掴む事故の防止） |
| 選ばれた ID が候補にあるか | その項目を捨てる |
| 件数が指定と合うか | 多ければ切り詰め、少なければ得点順に補う |
| チャンネルが空 | そのチャンネルだけ得点順の抽出に落とす |
| 要約に URL が混ざっていないか | 原文に差し戻す |
| 要約が 110 字以内か | 130 字までは切り詰め、超えたら原文に差し戻す |
| 日本語を含むか | 含まなければ原文に差し戻す |
| 全体で原文に差し戻した割合が 3 割を超えたか | run 全体を見送る |

結果は 1 行で出ます。

```
[COMPOSE] 検証: 採用 41 / 切り詰め 1 / 原文 3 / 破棄id 0 / 補充 7 / 救済 1（失格率 6.8%）
```

### 同じ材料でやり直す

中間ファイルが残っているので、収集をやり直さずに生成と投稿だけ試せます。

```bash
# 収集だけ（投稿されない）
./bin/python webex-news-rss-bot.py --emit-candidates log/compose/manual-001

# 生成だけ
./bin/python webex-news-rss-bot.py --compose log/compose/manual-001

# 投稿内容の確認（送信しない）
./bin/python webex-news-rss-bot.py --post-from log/compose/manual-001 --llm-mode compose --dry-run
```

## 自動実行

### macOS（launchd）

`run_rssbot.sh` を launchd から呼びます。plist は 30 分ごとに起動し、配信するかどうかはスクリプトが決めます。

```bash
cp run_rssbot.sh.example run_rssbot.sh && chmod +x run_rssbot.sh
cp webex-news-rss-bot.plist.example ~/Library/LaunchAgents/com.webex-news.rssbot.plist
launchctl load ~/Library/LaunchAgents/com.webex-news.rssbot.plist
```

plist の `ProgramArguments` で、配信時刻（時）と曜日を渡します。`12345` は月曜から金曜です。

```xml
<array>
  <string>/bin/bash</string>
  <string>/path/to/rss-bot/run_rssbot.sh</string>
  <string>9</string>
  <string>12345</string>
</array>
```

ラッパーは起動のたびに次を確認します。日本時間で判定するので、Mac のタイムゾーンを変えても動きます。

1. 指定の曜日か
2. 日本時間で配信時刻を過ぎているか
3. その日はまだ配信していないか（`log/.last_run_jst`）
4. ネットワークが通るか（`endpoints.yml` の `healthcheck:` に挙げた URL が**すべて** 200 を返すか）

実行中に Mac が寝ると名前解決が壊れて全チャンネルが失敗するため、`caffeinate` でスリープを抑えます。

### 終了コード

| 本体の終了コード | ラッパーの動き |
|:---:|:---|
| 0 | 「配信済み」を記録して終了 |
| 1 | 一部のスペースへ送れなかった。記録して終了 |
| 2 | 1 件も送れなかった。記録を残さず**30 分後にやり直す** |
| 3 | 生成を検証で落として見送った。記録を残さず**30 分後にやり直す**。ただし日本時間で配信時刻＋2 時間（既定 11 時）を過ぎていれば、簡易モードで配信する |
| 4 | 設定か入出力の誤り。やり直しても直らないので、**簡易モードでの配信を一度だけ試して**から記録して終了する |

簡易モードで配信した日は、投稿の末尾に `⚠️ 本日は簡易モードで配信しています` と出ます。
生成が静かに壊れたまま、それらしい投稿が毎朝届き続ける状態に気づけるようにするためです。

### Windows

`run_rssbot.bat` をタスクスケジューラに登録します。`自動実行を登録.bat` が登録まで行います。
JST ゲートと疎通確認は macOS 版と同じ考え方で動きます。

### `~/Documents` 配下に置く場合

（TCC の保護）。`deploy_to_launchd.sh` がホーム直下へ同期して launchd に登録します。

## 配信に失敗したときの動き

| 状況 | どうなるか |
|:---|:---|
| ネットワークが通らない | 最大 120 秒待って再確認。駄目なら配信を見送り、30 分後にやり直す |
| Webex への送信が失敗 | 5 秒、20 秒と待って最大 3 回やり直す。認証エラーは即座に諦める |
| 全チャンネル送信失敗 | 「配信済み」を記録せず、30 分後にやり直す |
| 一部だけ失敗 | 送れた分はそのまま。記録して終了する |
| 生成が通らない | 30 分後にやり直す。11 時を過ぎたら簡易モードで配信する |
| 該当記事が 0 件 | そのスペースには何も投稿しない |
| 環境変数が未解決のチャンネル | そのチャンネルだけスキップし、他は配信する |

### 特定のチャンネルだけ止める

`.env` の該当するスペース ID をコメントアウトします。変数が解決できなくなるので、
そのチャンネルだけスキップされます。

```bash
# WEBEX_SPACE_ID_ECONOMY=Y2lzY29zcGFyazovL3Vz...
```

## トラブルシューティング

### 記事が 1 件も集まらない

`--hours` を広げて確認します。フィード側が更新されていないだけのことがあります。

```bash
./bin/python webex-news-rss-bot.py --dry-run --hours 72
```

実行ログの「取得: URL → N 件」を見ると、どのフィードが空かわかります。

### 特定のチャンネルだけ投稿されない

起動時に `[WARN] channels.yml channel[N] (名前): webex_space_id の環境変数が未解決です` が出ていないか
確認します。`.env` に対応する変数が無いか、綴りが違います。

`[INFO] 該当ニュース 0 件` なら設定は正しく、その日は該当記事が無かっただけです。

### 意図した記事がカテゴリに入らない

`analyze_filter.py` で採点を見ます。必須語（`!` 付き）を 1 つも含まないと、
他の語が何点あっても不合格になります。

```bash
./bin/python analyze_filter.py
```

### `バックエンド claude は利用できません`

`claude` が見つかっていません。`~/.local/bin`、`/opt/homebrew/bin`、`/usr/local/bin` は自動で探すので、
それ以外に入れている場合だけ `.env` に絶対パスを書きます。

```bash
COMPOSE_CLAUDE_BIN=/your/path/to/claude
```

場所は `which claude` でわかります。

### `Failed to authenticate` で生成が止まる

`claude` の認証が切れています。対話ターミナルで長期トークンを発行し、`.env` に書きます。

```bash
claude setup-token
```

```bash
# .env
CLAUDE_CODE_OAUTH_TOKEN=発行された値
```

launchd から実行するときはログインセッションの keychain を読めないことがあるため、
この環境変数を使う方が確実です。

### 終了コード 3 が続く

生成結果が検証に落ちています。`log/compose/<run_id>/validation.json` に理由が残っています。
同じ材料で生成だけやり直せます。

```bash
./bin/python webex-news-rss-bot.py --compose log/compose/<run_id>
```

### 投稿の末尾に `⚠️ 本日は簡易モードで配信しています` と出る

生成が通らず、AI を使わない経路で配信しました。上と同じく `validation.json` と実行ログを見ます。

### 要約が英語のまま出る

`--llm-mode none` で配信されています。生成バックエンドが動いていません。

### 自動実行が動かない

登録されているかを確認します。

```bash
launchctl list | grep rssbot
```

`log/gate.log` に、配信を見送った理由が日付付きで残っています。曜日、時刻、当日配信済みのどれかで
止まっていることが多いです。

### SSL のエラーが出る

検査する SSL プロキシの環境では、`.env` で検証を切れます。**信頼できるネットワークでのみ**使ってください。

```bash
SSL_VERIFY=False
```
